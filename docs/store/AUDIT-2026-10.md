## 1. Verdict

**Yes, with fixes.** The core is sound: server-side pricing, a signed and idempotent webhook in one transaction, and admin auth on every route. These three things stand between it and 3 years of hands-off running:
1. **Orders can be recorded incompletely, with no error.** Only the first 10 line items are read (S-01). Lines paid at a price that was changed during checkout lose their variant and their stock decrement (S-02).
2. **Oversells and failures are invisible.** A last-unit race is clamped silently (S-04), and a session stays payable for 24 h (S-03). A failed webhook alerts nobody (S-06), and a failed confirmation email leaves no trace in the admin (S-05).
3. **Refund bookkeeping has edge cases that corrupt the moms report:** a currency mismatch under Adaptive Pricing (S-07, suspected), partial refunds spread over several months (S-08), and a refund that arrives before its order (S-09).

## 5. Keep as is

These are well built. The follow-up work must not churn them.

- **Webhook transaction design** (`route.ts:235-289`): the event-id ledger and the order insert share one transaction, with a UNIQUE `stripe_checkout_session_id` as backstop. Side effects (email, cache revalidation, newsletter) run only after COMMIT, and a failure rolls everything back for Stripe to retry. Signature checked per request, with a clear 500 when the secret is missing.
- **What was bought comes from Stripe** (`listLineItems`), never from client metadata. The cart cookie holds only `{variantId: qty}` (`cart.ts:44-48`). Stock, availability, terms acceptance and country are re-checked server-side at checkout (`cart/actions.ts:139-168`). Shipping is computed server-side from an allow-list (`shop-info.ts:40-77`).
- **Stock edits as deltas** (`previousStock`, `product-form.ts:482-490`; `setStock`), so a sale during an admin edit is never overwritten. `CHECK (stock >= 0)`.
- **Auth**: `requireSession()` in every admin page, server action and route handler (verified: products list/new/edit, `saveProduct`, `uploadProductPhoto`, `setStock`, orders page, `markShipped`, slip, moms page, moms CSV). Session tokens are stored hashed, passwords use scrypt with a dummy hash to equalise timing, there is no signup route, and cookies are `httpOnly`/`sameSite=lax`/`secure`.
- **Error codes instead of text in URLs** (`error-codes.ts`). Image URL allow-listing (`sanitizeImages`). JSON-LD `<` escaping. The `cs_` pattern check on the success page.
- **Catalog caching**: one `prices.list` per 5 minutes; catalog tag invalidation from both admin and webhook; cart and checkout read live rows. Result: 0 DB and 0 Stripe calls per storefront view on a warm cache. `CACHE_SCOPE` keeps preview and production apart.
- **Preview DB guard** (`prepare-preview-db.mjs:30-58`): an endpoint allow-list plus a test-key check.
- **Withdrawal flow**: every notice is recorded, matched or not; whether it matched is never revealed; the acknowledgement is tracked in `acknowledged_at`; it sits outside the store-closed gate.
- **Moms logic**: pure and tested (`moms.ts`); dates in Swedish time; CSV with BOM and decimal commas; non-SEK orders listed rather than dropped.
- **Single sources**: `shop-info.ts` (seller, shipping, rights) and `legal-text.ts` (terms page and email share the wording).
- **Soft delete**: products are hidden, never deleted. Order items use `ON DELETE SET NULL` and keep a `variant_label` snapshot.
- **Dependency surface**: next, react, pg, stripe, resend, plus 4 small UI utilities. Keep it.
- **The migration doctrine**: re-runnable SQL, migrate before merge, DESTRUCTIVE changes in their own PR. It is enough at this size; just fix the README wording (S-19).

     ```ts
     /** Stripe's line.price.product: an id, or an expanded (possibly deleted) product. */
     export function stripeProductId(product: string | { id: string } | null | undefined): string | null {
       if (!product) return null;
       return typeof product === "string" ? product : product.id;
     }

     /**
      * The variant a paid line belongs to: by price id, else by Stripe product id.
      * A price edited in the admin gets a new price id, but the variant keeps its
      * Stripe product, so a checkout opened before the edit still maps back.
      */
     export function matchVariant<V extends { stripe_price_id: string; stripe_product_id: string }>(
       variants: V[],
       priceId: string | null,
       productId: string | null,
     ): V | null {
       return (
         (priceId ? variants.find((v) => v.stripe_price_id === priceId) : undefined) ??
         (productId ? variants.find((v) => v.stripe_product_id === productId) : undefined) ??
         null
       );
     }
     ```

      * The refunded amount in the order's own currency (öre for a SEK order).
      * With Stripe Adaptive Pricing the charge can be in the customer's currency
      * while the order is recorded in SEK; then convert in proportion to what the
      * order recorded. A full refund is the whole order.
      */
     export function refundedInOrderCurrency(
       order: { amount_total: number; currency: string },
       charge: { amount: number; amount_refunded: number; currency: string; refunded: boolean },
     ): number {
       if (charge.currency.toLowerCase() === order.currency.toLowerCase()) return charge.amount_refunded;
       if (charge.refunded) return order.amount_total;

     }

## 7. Explicitly not recommended

| Considered | Why rejected for this plateau |
|---|---|
| Stock reservations now | They need a reservations table, a new webhook event and release logic. At 5–30 orders a week, a 30-minute session plus an oversell alert (P1-02, P1-03) is enough. Revisit under P3-04's trigger. |
| Queues/background jobs (Inngest, QStash, Vercel Queues) for email or webhooks | Stripe already retries webhooks for 3 days. Emails are sent after commit, and failures are now visible (P1-06). A queue adds a vendor and a failure mode. |
| Redis/Upstash rate limiting | One DB count (P1-07) plus Vercel Firewall rules cover the abuse cases. |
| Error-tracking SaaS (Sentry etc.) | The three failures that matter (webhook, confirmation email, oversell) now email desk@. Another account and SDK isn't justified by about 1 order a day. |
| Migrating `unstable_cache` to `use cache` / Cache Components now | It works in Next 16, and switching on `cacheComponents` changes rendering semantics site-wide. Only do it when forced (P3-03). |
| Moving photos off Stripe Files (Vercel Blob/S3) | It works at no cost, and photos are re-uploadable from the originals. Only migrate if Stripe restricts `business_logo` links. |
| Storing prices in Postgres / `price_data` at checkout | That would make the DB the price authority and change the tested money path. The per-variant Stripe price model is fine once the webhook maps by product (P1-01). |
| An ORM or a migration framework (Prisma, Drizzle, node-pg-migrate) | Six re-runnable SQL files and one person do not need a ledger table or a new dependency. The doctrine in the README is enough. |
| Indexes on `shop_order_items(shop_order_id)` / `shop_orders(created_at)` | At ≤ 7,000 item rows and ≤ 4,700 orders after 3 years, sequential scans take well under 10 ms. Add them if a query ever shows up as slow. |
| Paginating the moms query | `loadMomsRows` reads ≤ 4,700 rows, a few hundred KB, once per admin view. |
| Middleware/proxy-based admin auth | Per-route `requireSession` is correct for server actions (which middleware doesn't fully cover). P2-06's guard test closes the "forgot it" risk more simply. |
| Nonce-based CSP | It forces dynamic rendering of every page. `unsafe-inline` is the documented gap; the store has no user-generated HTML. |
| Stripe Tax / OSS registration now | Not needed under the €10,000 EU threshold, which the moms page already tracks. |
| Customer accounts, a CMS, a new framework, moving off Vercel or Neon | Nothing at the plateau requires them. |
| Neon direct (unpooled) connections for runtime | The pooled URL with max 5 per instance is the right setting for serverless. |
